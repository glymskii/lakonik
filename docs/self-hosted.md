# Корпоративный контур: сервер заказчика и вход по коду организации

Заказчик (ADV Kazakhstan) хочет, чтобы записи, расшифровки, отчёты и учётные записи сотрудников жили на его сервере,
а не у разработчика. При этом дорабатывать код он не планирует — ему нужна гарантия, что к данным нет доступа ни у
кого, кроме его сотрудников. Отсюда схема: **одно приложение в App Store, несколько независимых серверов.**

## 1. Как это выглядит для пользователя

```
Экран входа
├── Личный            → сервер разработчика (api.lakonik.app), личные встречи, подписка
└── Корпоративный     → код организации («ADV») → приложение узнаёт адрес сервера компании
                        → почта @advgroup.kz → код из письма → всё дальше только с сервером компании
```

Переключение режима = выход из аккаунта: одновременно активен один сервер (полноценные параллельные пространства —
после фазы 1 «организации», см. `lakonik-1.0.md`).

## 2. Как код организации превращается в адрес сервера

`GET https://api.lakonik.app/api/org-servers/ADV` → `{ code, name, apiBaseUrl, hint }`

- Запрос содержит **только код организации** — ни почты, ни устройства, ни персональных данных.
- Реестр задаётся переменной окружения `ORG_SERVERS` (JSON-массив) на сервере разработчика; добавление компании —
  одна строка, без релиза приложения.
- Ответ кешируется в приложении (`AppConfig.selectOrg`); дальше **все** запросы (вход, аудио, отчёты, задачи, SSE)
  идут только на `apiBaseUrl` компании. Разработчик не видит ни трафика, ни данных.
- Если справочник недоступен, вход в уже выбранную организацию продолжает работать: адрес сохранён на устройстве.
- Запасной вариант для закрытых контуров — ввод адреса сервера вручную (сейчас доступен в Debug-сборке,
  в релизной включается по запросу).

Реализация: сервер — `apps/server/src/api/routes/org-servers.ts`, клиент — `AppConfig`, `APIClient.orgServer(code:)`,
`Auth/SignInView.swift` (сегмент «Личный / Корпоративный»).

## 3. Что разворачивается у заказчика

`deploy/` — готовый комплект: `docker-compose.yml`, `Caddyfile`, `.env.example`, `README.md` (инструкция админу).

```
[iPhone сотрудника] ──HTTPS──▶ Caddy (TLS) ──▶ api ──┬──▶ postgres  (аккаунты, транскрипты, отчёты, задачи)
                                              worker ─┴──▶ minio     (временное аудио, удаляется после расшифровки)
                                                  │
                                                  ├──▶ api.elevenlabs.io   (аудио → текст)
                                                  ├──▶ api.anthropic.com   (текст → отчёт)
                                                  └──▶ Resend / SMTP       (коды входа)
```

Всё в одной сети Docker, наружу открыт только Caddy. Образ приложения — приватный `ghcr.io/glymskii/lakonik-server`
(read-only токен для их админа), поэтому кодовая база остаётся закрытой, а сервер полностью под их контролем.
Требования: 2–4 vCPU, 4–8 ГБ RAM, 50–100 ГБ SSD, Ubuntu + Docker, DNS-имя и открытые 80/443.

## 4. Что остаётся на стороне разработчика

| Что | Почему | Данные компании |
|---|---|---|
| Справочник организаций (`/api/org-servers/{code}`) | чтобы сотрудник вводил «ADV», а не URL | нет, только код → адрес |
| Сборка и публикация образа, обновления | чтобы заказчик не вёл кодовую базу | нет |
| Приложение в App Store, сертификаты, Apple Developer | одна запись в магазине на всех | нет |
| Push-relay (планируется) | ключ APNs принадлежит команде Apple разработчика и не передаётся | только device token и тип события («отчёт готов»), без содержимого |

До запуска relay push-уведомления в корпоративном контуре не приходят: прогресс обработки виден по SSE, пока
приложение открыто, и в списке встреч после обновления. Это единственная функциональная разница.

## 5. Порядок внедрения для ADV

1. Админ поднимает сервер по `deploy/README.md`, получает токен к образу, называет домен (например `meetings.advgroup.kz`).
2. Разработчик добавляет запись в `ORG_SERVERS` на api.lakonik.app → код `ADV` начинает работать в приложении.
3. Перенос текущих данных пилота с сервера разработчика: `pg_dump` → восстановление в их базу (аудио переносить
   нечего — оно удаляется после расшифровки). После проверки данные пилота на сервере разработчика удаляются.
4. Тестовая группа входит корпоративным способом, проверяет запись → расшифровку → отчёт → экспорт.
5. Дальше: push-relay, затем (по фазам `lakonik-1.0.md`) организации и интеграции с записями Meet/Zoom —
   в корпоративном контуре они настраиваются ключами самой компании.

## 6. Ограничения, о которых нужно сказать заказчику честно

- **Внешние AI-сервисы остаются внешними.** Расшифровка (ElevenLabs) и отчёт (Anthropic) — облачные API: на их
  моделях данные не обучаются и не хранятся после обработки, но аудио и текст туда уходят. Полностью локальный
  вариант — отдельный проект: сервер с GPU, заметно хуже казахский и разделение говорящих.
- **Ключи и счета — на стороне компании**: ElevenLabs и Anthropic оплачивает ADV, примерно $0.45 за час встречи.
- **Обновления версии** — их админ выполняет `docker compose pull && up -d`; график согласуется.
- **Резервные копии и доступность** — зона ответственности их ИТ (в инструкции есть готовый cron с `pg_dump`).
